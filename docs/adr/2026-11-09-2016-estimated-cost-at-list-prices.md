# Estimate dollar cost per API response from a local price table

**Status:** accepted

**Context:** The dashboard showed tokens but not dollars. Claude Code's `cost-state` has a dollar figure, but only as a running total per session: it cannot be split by day, by subagent or by host, and it includes side requests (titles, summaries) that leave no transcript record.
**Decision:** `pricing.py` holds API list prices per model (input, output, cache read; cache writes at 1.25x input for the 5-minute TTL and 2x for the 1-hour TTL, using each response's `ephemeral_1h_input_tokens`), matched by longest id prefix after dropping date suffixes and `[1m]`. Each message is priced when stored (`usd` column); `thread_stats` and `sessions` sum it. A change to `pricing.VERSION` re-prices every stored row and rebuilds all rollups on the next refresh without re-parsing. Models with no price count $0, and `/api/models` reports them as `priced: false`.
**Alternatives:** use `cost-state`: it is per session only. Compute at query time from per-model token sums: long-prompt tiers (Haiku 5.5 above 100K) need per-response prompt sizes, and session rollups would need per-model breakdowns.
**Consequences:** The figure is an API-equivalent estimate, not a bill: it ignores subscriptions, fast mode (none in the data so far), web-search fees and partner pricing. Checked against `cost-state` on the hub's data, priced on `cost-state`'s own token counts, Opus 4.8, Opus 5, Opus 5.5, Sonnet 5 and Haiku 4.5 agree within the 5m/1h write split. Sonnet 5.5 comes out 0–33% above Claude Code's figure, and the gap grows with cache reads, so Claude Code's internal rate seems to have changed over time; the list price ($0.20 per MTok for cache reads) is kept. Transcript-based totals run below `cost-state` (about 75–94% for Opus) because side requests are missing.
